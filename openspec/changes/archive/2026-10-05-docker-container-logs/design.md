# Design

## Context

Контейнер запускает `cron -f` как PID 1 (`Dockerfile`). Задание в `/etc/cron.d/calendar_bot` перенаправляет вывод в `/var/log/cron.log`, а Docker собирает только stdout/stderr PID 1, поэтому `docker logs` пуст. Cron также запускает задания с пустым окружением, поэтому переменные из `docker-compose.yml` в скрипт не попадают. Скрипт читает конфигурацию через `os.getenv` после `load_dotenv()`. См. proposal.md для мотивации.

## Goals / Non-Goals

**Goals:**
- Вывод cron-задачи виден в `docker logs`.
- Строки не задерживаются буферизацией Python.
- Cron-задача видит четыре переменные конфигурации без правок кода бота.

**Non-Goals:**
- Структурированные логи, временные метки, ротация.
- Передача произвольных переменных окружения и их обновление без перезапуска контейнера.

## Decisions

1. **Перенаправлять вывод задачи в `/proc/1/fd/1` и `/proc/1/fd/2`** (`>> /proc/1/fd/1 2>> /proc/1/fd/2`) вместо `/var/log/cron.log`.
   Причина: это стандартный приём для cron в Docker, не требует правок кода и сохраняет разделение stdout/stderr.
   Альтернативы: `tail -f /var/log/cron.log` как фоновый процесс в `CMD` (нужен второй процесс, сложнее остановка и перезапуск); логирование из Python напрямую в stdout (не сработает, у cron-процесса нет доступа к stdout контейнера, перенаправление всё равно нужно).

2. **Запускать Python с `-u`** (или задать `PYTHONUNBUFFERED=1`) в cron-строке.
   Причина: при выводе не в терминал stdout буферизуется блоками, строки появились бы только при завершении. Флаг в cron-строке работает независимо от окружения cron.

3. **Удалить `touch /var/log/cron.log`** из `Dockerfile`, так как файл больше не используется.

4. **Entrypoint `entrypoint.sh` записывает `/app/.env` и запускает `exec cron -f`.**
   Он берёт только `GOOGLE_API_KEY`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_GROUP_ID`, `CALENDAR_ID`, пишет их в формате `KEY="value"` и выставляет права `0600`. `exec` оставляет cron PID 1, что нужно для `/proc/1/fd/*`.
   Причина: `calendar_bot.py` уже вызывает `load_dotenv()`, а `find_dotenv` ищет `.env` рядом со скриптом (`/app`), поэтому код бота не меняется. Файл создаётся в рантайме и в слои образа не попадает.
   Альтернативы: подгружать файл с переменными в cron-строке через `. file` (значения со спецсимволами ломают разбор в `sh`); писать `printenv` в `/etc/environment` (cron из Debian не читает его для заданий в `/etc/cron.d`); менять код бота на чтение `/proc/1/environ` (хрупко и завязывает код на Docker).

## Risks / Trade-offs

- [Секреты лежат в `/app/.env` внутри контейнера] → Файл создаётся при старте с правами `0600`, доступен только root, в образ не попадает. Значения не печатаются в логи.
- [Переменные фиксируются при старте контейнера] → Изменение `.env` на хосте требует перезапуска (`docker compose up -d`), это ожидаемо.
- [Значения с символом `"` или переводом строки сломают формат `KEY="value"`] → Для токенов, ID чата и ключа API такие символы не используются. Ограничение записано в README.
- [Запись в `/proc/1/fd/*` требует, чтобы cron работал от root и был PID 1] → Так и есть сейчас (`root` в cron-строке, `CMD ["cron", "-f"]`).
- [Старые логи в `/var/log/cron.log` пропадут при пересборке] → Приемлемо, файл не использовался как источник истины.
