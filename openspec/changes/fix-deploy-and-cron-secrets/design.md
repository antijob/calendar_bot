# Design

## Context

- Деплой (`.github/workflows/deployment.yml`, job `deploy`): `docker stack deploy` и сразу за ним `docker service update --force`. `stack deploy` уже запускает rolling update (`start-first`, задержка 10 с), второй вызов конфликтует с ним.
- Продакшен задаёт секреты как `GOOGLE_API_KEY_FILE` и `TELEGRAM_BOT_TOKEN_FILE` (`docker-compose.prod.yml`). `calendar_bot.py` читает их через `_read_secret`, но `entrypoint.sh` сохраняет для cron только четыре прямые переменные.
- Ошибки `googleapiclient` и `requests` содержат URL запроса с `key=` и `bot<token>`. Вывод cron теперь идёт в `docker logs`.
- См. proposal.md для мотивации.

## Goals / Non-Goals

**Goals:**
- Один успешный rolling update за деплой.
- Секреты в прод-схеме доходят до cron-запуска без копирования значений в `.env`.
- Ни ключ, ни токен не попадают в вывод ошибок.

**Non-Goals:**
- Проверка состояния сервиса после деплоя (health-check) и автоматический откат.
- Редактирование секретов в выводе, который печатает сам бот вне исключений.

## Decisions

1. **Убрать `docker service update --force`, оставить `docker stack deploy --resolve-image always`.**
   Образ с нужным тегом уже задан в compose через `${IMAGE_TAG}`, а `--resolve-image always` заставляет Swarm взять актуальный дайджест.
   Альтернативы: оставить `service update` с повтором и паузой (маскирует гонку, удлиняет деплой); добавить `--detach=false` в `service update` (ждёт сходимости, но второе обновление всё равно избыточно).

2. **Блок `concurrency: { group: deploy-prod, cancel-in-progress: false }` на job `deploy`.**
   Причина: два коммита подряд не должны давать конкурирующие обновления, а идущий деплой нельзя обрывать на середине.

3. **Добавить `GOOGLE_API_KEY_FILE` и `TELEGRAM_BOT_TOKEN_FILE` в список переменных `entrypoint.sh`.**
   В `/app/.env` попадают пути, а не значения секретов, поэтому в файле на диске контейнера секрет не дублируется. Если `*_FILE` не задан, пишется пустое значение, как и для остальных переменных. Бот дальше читает файл через `_read_secret`.
   Риск: пустая `GOOGLE_API_KEY=""` в `.env` не должна перекрывать значение из `*_FILE`. `_read_secret` сначала смотрит `*_FILE`, поэтому порядок корректен.

4. **Верхнеуровневый обработчик в `__main__` с редактированием секретов.**
   `main()` вызывается в `try/except Exception`: текст трассировки (`traceback.format_exc()`) очищается от значений `API_KEY` и `TELEGRAM_BOT_TOKEN` (замена непустых значений на `***`), печатается в stderr, процесс завершается кодом 1.
   Причина: покрывает сразу `HttpError` (URL с `key=`) и `requests`-исключения (URL с токеном), не меняя вызывающий код. Редактирование по значению надёжнее регулярных выражений по формату URL.
   Альтернативы: перехватывать отдельно `HttpError` и печатать только статус (не покрывает `requests`); регулярное выражение по `key=` и `bot<...>` (хрупко при смене формата URL).

## Risks / Trade-offs

- [Секрет короче нескольких символов или пустой может замаскировать лишнее] → Маскировать только непустые значения; для токенов и ключей API длина достаточна.
- [Редактирование не поймает секрет, преобразованный до вывода (например, URL-кодированный)] → Значение ключа и токена в URL используется как есть; кодированная форма дополнительно маскируется через `urllib.parse.quote`.
- [Лог `print(f"Ответ Telegram API: {response.text}")` выводит ответ API] → Ответ Telegram не содержит токен; меняем только вывод исключений.
- [Зависимость от незаархивированного change `docker-container-logs`] → Сначала архивировать его (после ручной проверки), затем применять этот change.
- [Деплой без `service update --force` не перезапустит сервис при неизменном теге и дайджесте] → Для этого случая есть ручной запуск workflow с `Force build`, который собирает новый образ.

## Migration Plan

1. Влить изменения в `main`: деплой пойдёт по исправленному workflow.
2. После деплоя проверить `docker service ps antijob_calendar_scheduler`: одно обновление, задача в состоянии running.
3. Откат: вернуть предыдущий тег образа через `docker service rollback antijob_calendar_scheduler`.
